# 当前原生核心 RAM 占用

2026-10-06，基于当前18-PBS布局修复后的源码。分析对象为SDL/MCU共用的原生Animator，排除参考80×24核心、SDL、PCM和Windows运行库。表内对象大小已同步本次float天气（减少120 B）；工作区/历史等容量未改。最新验证见 [NATIVE_FLOAT.md](NATIVE_FLOAT.md)。

使用Clang Cortex-M3 soft-float ABI编译sizeof/offsetof常量；主机运行3种子×6起点、每组原始/插桩回放，共各72132帧。逐回放字符、framebuffer、主RNG摘要一致。可复现工具为 `tools/profile_ram.py` 和 `tools/profile_ram.c`；改为float前的分析保存在 [ram-breakdown](validation/2026-10-06/ram-breakdown/README.md)，当前重新测量的ABI、回放及栈数据保存在 [float-weather](validation/2026-10-06/float-weather/README.md)。

## 1. 一个Animator的完整拆分

| 内容 | ARM字节 | 占整个对象 | 说明 |
| --- | ---: | ---: | --- |
| 文本可写副本 | 11350 | 32.7% | 18份文本，包含终止符；初始化全部复制 |
| WordLine分行表 | 4260 | 12.3% | 355条，每条12 B，指针/长度/词数 |
| 历史条目数组 | 3648 | 10.5% | 240+48+16条，每条12 B |
| scratch临时工作区 | 1024 | 2.9% | 实例持有，重复使用，不是每帧分配 |
| 字符画布 | 4812 | 13.8% | 1200格×4 B，加12 B元数据 |
| framebuffer | 4096 | 11.8% | 唯一的256×128、1bpp缓冲 |
| 主MT19937随机状态 | 2512 | 7.2% | 624个uint32，加索引/计数/对齐 |
| 三份海洋状态 | 1488 | 4.3% | 每份496 B，其中480 B字符 |
| 五份天气状态 | 160 | 0.5% | float版每份32 B |
| 其余描述符、调度、播放器、计数及对齐/余量 | 1402 | 4.0% | 完整成员与offset见summary.json |
| **合计** | **34752** | **100%** | **33.94 KiB；尚未含栈/驱动/目标libc** |

最大的部分是文本及其分行表：15610 B，占44.9%。两块显示缓冲合计8908 B，占25.6%。历史条目保存行指针、颜色和前缀指针，并没有为每条历史再复制整段文本。

核算层次：Credits=30544 B；播放器72 B；fb4096 B；包装配置/计数40 B，合计34752 B。Credits内部已经包含20384 B工作区，不能再加一次旧堆峰值。Windows x64对象为40504 B，指针较大；不要用它替代ARM数字。

## 2. 固定工作区与实际使用

ARM工作区storage联合体占20384 B（19.91 KiB），其中bytes数组可用20378 B。有效预留载荷20282 B、各次预留间对齐26 B，余下70 B可用空间加6 B联合体尾部对齐，共76 B。32次预留全部发生在初始化，播放期间预留次数和used不变。核心无显式malloc/realloc/free；固定工作区消除了分配抖动，但没有自动减少持久驻留的内容。

| 项目 | 预留 | 本次回放峰值 | 理论可收紧余量 |
| --- | ---: | ---: | ---: |
| scratch | 1024 B | 最大请求551 B | 473 B |
| history[0] | 240条 / 2880 B | 173条 / 2076 B | 804 B |
| history[1] | 48条 / 576 B | 28条 / 336 B | 240 B |
| history[2] | 16条 / 192 B | 13条 / 156 B | 36 B |

三组历史的214条峰值确实同时出现于完整回放的6025拍，不能直接取三者最大值173来代替总占用。它们当时仍被结构体保留，不表示全部仍在显示。能否提前释放/复用需分析未来引用。

仅收紧上述容量约省1553 B，对象仍约33199 B，远大于20 KiB。这些峰值来自受控回放，不是任意未来内容/控制输入的容量证明；没有据此直接修改数组大小。

## 3. 为什么文本要占这么多RAM

`data_init` 当前把18份源字符串全部复制到可写工作区，再执行初始化随机破坏；按词播放的文本还会将换行改成NUL，并生成WordLine数组。因此即使内容在Flash已有一份，RAM仍保留副本和指针表。所有场景的数据都在初始化时常驻，没有按场景复用。

本次数据统计：

- 7447 B文本副本属于完全没有初始化随机破坏的模板，适合优先评估导出为可直接引用的Flash结构。
- 其余副本共3903 B；其中真正标记为需要随机破坏的源片段共1951 B。不是整份混合模板都需要随机化。
- 355条WordLine在初始化后作为索引读取，4260 B是另一笔独立支出。采用Flash中的偏移/长度表可能消除这笔RAM，但需要改读取接口，不能只给现有指针加const。
- 历史保存WordLine指针。按场景复用文本时必须处理历史引用，否则会出现显示旧历史时读到新场景数据的问题。
- 初始化随机调用顺序目前也是行为的一部分；延迟生成某场景随机文本不能悄悄改变后续RNG。

因此文本的主要方向是改变数据表示和生命周期，而不是减少几个malloc调用。

## 4. 对象之外

- 源码还有 `apply_event` 的静态空WordLine[2]，ARM声明大小24 B。当前主机单头实现对象实际.data=32 B、.bss=0，与该数组的主机大小吻合。噪声字符串指针数组在源码中可写，但当前优化后的主机对象未保留为可写符号；目标是否如此须由目标map确认。
- 调用栈没有包含在34752 B内。当前x64 Release单函数静态栈较大者为场景回调440 B、天气绘制392 B、天气修改232 B、文字流函数200 B。这不是完整调用链峰值，更不是Cortex-M3栈预算，不能相加所有函数或只取最大值当作最终栈。
- 驱动状态、DMA描述符、应用全局变量、ISR保存上下文和目标libc开销均另算。DMA可借用这张fb，不必再分配4096 B发送副本，但传输期间不得更新它。
- 原生仍有整数格式化/sscanf等libc依赖；浮点格式化已移除。核心无显式堆调用，不等于所选目标libc内部绝不分配。
- 字形和离散数学表属于只读数据；字体/10905 B数学表不算入上述可写对象RAM。实际Flash和完整静态RAM须在目标链接脚本下验证。最新F401声明式编译栈和指令检查见NATIVE_FLOAT.md，仍未完成目标链接。

## 5. STM32F103C8T6结论与可选方向

20 KiB SRAM=20480 B，仅当前对象就超出14272 B，尚未计栈及驱动。不是把芯片配置成XIP就能解决；这里讨论的正是可写RAM。隐藏PBS19–24只减少绘制，不改变固定1200字符格或其他状态容量。

优先级建议（仅分析，尚未实施）：

1. 文本和分行索引改成Flash可读的数据表示，保留少量真实可变内容。这比显示缓冲省几个字节更有潜力。
2. 历史记录改成紧凑索引，并明确何时可回收；当前每条12 B主要是三个指针。不能仅根据当前可见行数裁掉历史。
3. 原生char_buf若改16位字符/属性编码，理论省2400 B；需保留实际用到的字形、背景和光标语义并回归。fb保持4096 B。
4. 若证明确实无重叠生命周期，可复用三份海洋状态，理论最多省992 B；当前尚未做这个证明或改动。
5. 替换MT19937可以省约2.5 KB，但会改变整条随机序列，属于行为取舍，不应作为无损优化。

即使理想化地省掉7447 B无随机文本副本、4260 B分行表，再收紧1553 B历史/scratch，对象仍约21492 B，尚未含栈。几个局部容量调整不足以保证装入20 KiB；需要组合的数据表示优化，并在真实目标上链接和测量。
