# MCU 内存与热点分析

> 阶段资料：本文的测量、路径和“当前/待办”措辞仅适用于所述版本，不是继续开发指令。现行接入见 [ANIMATOR_API.md](ANIMATOR_API.md)，最新资源与调试边界见 [HANDOFF.md](HANDOFF.md)。

2026-10-05，分析基线 d563697。未修改业务实现、随机算法或布局。

## 测量边界

使用 `tools/profile_core.py` 独立构建无 SDL、无终端输出、无音频的核心驱动。
计时构建使用原始核心；计数构建只改写 build 目录中的源码副本。每个 seed 运行
0–6508 拍，逐拍生成 60×20 布局和 framebuffer。两个构建的字符格和像素串流
64 位 FNV-1a 摘要相同，销毁后跟踪 live 为零。计数器不是采样 profiler，
调用数包括可能被编译器内联/消除的源码操作，不能当成真实 CALL 指令数或耗时排名。

复现（Windows Clang/LLVM-MinGW）：

```powershell
C:/ProgramData/miniconda3/python.exe tools/profile_core.py --cc D:/credits_vfd/.tools/llvm-mingw-20260922-ucrt-x86_64/bin/clang.exe
```

结果位于 build/profile-core；本轮 JSON 保存在 docs/validation/2026-10-05/core-profile。
工具同时对头文件做 ARM EABI 编译期 sizeof 探测（arm-none-eabi / cortex-m4）；
这只是明确的 32 位 ABI 样本，不表示选择了 MCU，也不表示固件已编译、链接或运行。
宿主计时受缓存、运行库和调度影响，不外推 MCU 时间或 XIP cache miss 成本。

## RAM：排除宿主，分离 XIP

代码、字体、事件表、字符串字面量及其他 const 数据，在链接脚本正确放入只读 XIP
区域时不计入常驻 RAM。Windows CRT、MinGW 启动、SDL、音频 PCM、主机输出缓冲
均不进入下表。目标运行库实际需要的 .data/.bss/堆管理状态需在目标 map 中另计。

| 对象 | x64 主机 sizeof / 实测 | ARM 32 位 sizeof / 轨迹投影 |
|---|---:|---:|
| Credits（已包含 Canvas、海洋、RNG 等） | 23,728 B | 23,208 B |
| Layout60 | 4,804 B | 4,804 B |
| Framebuffer | 4,096 B | 4,096 B |
| seed 1 动态请求峰值 | 100,284 B | 91,568 B |
| 合计 | 132,912 B | **123,676 B / 120.78 KiB** |

ARM 堆值不是板上实测：按每次分配/释放轨迹，将 Section 从 40 改为 28 B、
WordLine 从 16 改为 12 B、HistoryEntry 从 24 改为 12 B，其余分配字节数不变，
重新累计全程峰值。seed 0/1/42 的投影峰值分别为 91,412 / 91,568 / 91,756 B，
均在 beat 3007；对应合计 120.63–120.96 KiB。假设目标逻辑轨迹与主机一致。

以上不包括调用栈、ISR/RTOS 栈、驱动/DMA 缓冲、分配器元数据、对齐碎片，
也不计 realloc 实现内部可能短暂同时保留的新旧块。不能据此宣称 128 KiB RAM 足够。
另有 credits.c 的非 const 静态空词行数组，ARM ABI 为 24 B；是否被编译器移入只读
区需看目标产物，保守计入 RAM。故表中是主要对象小计，不是完整固件 RAM 总量。
已有 x64 静态栈报告中 canvas_clear 为 7,736 B、ocean_update 为 3,416 B，
只能用于定位风险；MCU 栈须重新编译并测高水位，不能直接加主机单函数最大值当总栈。

ARM Credits 内主要成员：Canvas 9,628 B，三个 Ocean 9,624 B，RNG 2,512 B。
这三项已占 21,764 B；指针变小仅使整个 Credits 减少 520 B。

## 分配热点：画布优先

seed 1，全曲含初始化，共 90,225 次 mem_resize（内部为 realloc，NULL 表示新分配）。
初始化 28 次，17,030 B 主机堆；ARM 投影初始化为 15,610 B。

| 分配位置 | 次数 | 主机全局堆峰值时存活 | 同时刻 ARM 投影 |
|---|---:|---:|---:|
| canvas.c reserve 字符缓冲 | 89,723 | 59,868 B | 59,868 B |
| canvas.c insert 分组数组 | 5 | 19,840 B | 13,888 B |
| data.c 原始文本副本 | 18 | 11,350 B | 11,350 B |
| data.c 词行描述 | 10 | 5,680 B | 4,260 B |
| credits.c 共享 scratch | 4 | 858 B | 858 B |
| text.c 历史条目 | 7 | 2,688 B | 1,344 B |
| text.c multiline 临时数组 | 458 | 0 B | 0 B |

画布字符缓冲占分配次数 **99.44%**：其中 89,721 次为 NULL 新分配，仅 2 次扩容。
其累计请求量 16,486,756 B 是流量，不是 RAM 峰值；总解码 47,273 次、构造 Section
37,205 次。当前 decode 分配后又复制到 Section，render 后释放；重叠处理还会切片复制。
因此仅改 realloc 增长倍数或缓存一个大缓冲，不能自动消除主要开销。

优化顺序建议：

1. 先区分解码临时区与本帧 Section 持有区，复用前者；研究把解码结果直接写入目标
   存储，减少一次分配/复制。再评估按帧有界 arena 是否能替代短命块；必须统计全帧
   累计需求，不能用 live 峰值直接当 arena 容量。保持原分组排序、合并、换行、属性继承。
2. 明确分组表容量与帧内峰值，复用已有表。当前表本来就在跨帧复用，只有 5 次分配，
   它主要是容量问题，不是频繁分配问题。不要凭三个种子直接冻结容量上限。
3. 文本副本不能因为 XIP 就直接删除：初始化会随机损坏字符，并把换行原地改成 NUL。
   可研究 Flash 常量文本 + 行区间描述 + 必要的可变副本/稀疏修改记录；逐项保持导入时
   RNG 消耗和字符串语义，不能改成场景开始时才随机初始化。
4. 小而确定的压缩随后做：光标 byte 数组转 bitset 可省 1,680 B；三个海洋字符数组在
   当前字符集合下从 uint32_t 改 uint8_t 可省 7,200 B，但仍须覆盖所有读写和输出转换。
   通用字符缓冲还含光标标志，不能未经编码设计就直接缩成 uint16_t。

## 时间与高频操作

原始核心 -O3，三个种子每帧平均（主机计时，约值）：

| 阶段 | µs/帧 |
|---|---:|
| 动画 + canvas_render | 3.75–4.03 |
| 60×20 排版 | 3.12–3.28 |
| 全屏字体光栅化 | 12.95–13.14 |

本驱动每个逻辑拍都做布局/光栅化；实际播放器补拍只需呈现最后一帧。
计数构建有额外开销，其 JSON 中的时间不用于以上结果。摘要计算在计时段外；计时含
时钟读取开销，不能用于亚微秒级函数排序。

seed 1 源码逻辑调用：glyph_bits 7,810,800；布局 space 12,049,011；
random_u32 1,477,061；random_unit 632,602；memcpy 60,640；memmove 97,347。
小 helper 很可能内联，次数多不等于函数调用开销大。目前主机的最大阶段为光栅化，
但 MCU 的软 double、堆分配和 XIP 缓存可能改变排名。

后续先在目标上分阶段测 cycle，再决定是否缓存字形展开行、跳过像素确定不变的格、
做 framebuffer 差分传输。仍需绘制空格背景、清除旧光标和保留显示节拍；不能简单
“遇空格就跳过”。显示总线吞吐另测，不混入核心计算结论。

## 会带入库代码的调用（bloat 候选）

对实际 credits_core 静态库执行 llvm-nm --undefined-only，确认核心引用了
realloc/free、sscanf、snprintf、sin/cos/pow/floor，以及错误路径 fprintf/abort。
Windows 特有的栈探测和 CRT 符号不属于目标预算。没有用 Windows EXE .text/.rdata
推算 MCU Flash，也未声称下列调用各自占多少字节；需目标库和链接 map 才能归因。

- **sscanf：30 次。** 只解析已知 CLEAR 指令的整数，适合改为小型有界解析器，通常比
  优化算术更值得先研究代码体积；保留失败检测。
- **snprintf：2,057 次。** 包含日期/整数/补空格以及天气 `%.2f`；浮点格式化可能带入
  较大的转换代码。应先看目标链接是否拉入 float printf，再评估专用格式化；不能用
  随意四舍五入代替原有格式语义。
- **sin 4,044、cos 1,014、pow 2,955、floor 14,099 次。** 除 Flash 外，软 double
  目标还有周期成本。只有受限、离散的参数域才适合预计算；先验证范围及取整边界。
  XIP 中的查表也有读带宽和缓存代价。不要盲目切 float 或替换 RNG。
- **fprintf/abort：错误路径。** 未来以目标错误回调替代宿主诊断，是干净的适配点；
  不能删除越界/容量检查来省代码。
- 目标构建再比较 -Os/-O2、function/data sections + gc-sections、LTO 的 map 与
  周期数据。静态库成员粒度可能保留同文件未使用函数；Flash 缩小与 XIP 命中率改善
  需要实际证据，不预设激进内联一定更快。

本轮只建立测量和分析，尚未实施上述优化。未测目标 Flash、板端 RAM/栈、总线、
cache miss、音频 DMA，也未覆盖任意种子/所有交互路径的资源上界。
